# Decisions taken while building this branch

Sixty-four rulings made during a subagent-driven build of the seventeen-task plan.
Each was a decision made without asking the author, under a standing instruction to
keep going. They are preserved here because the working ledger they came from is
scratch and gets deleted; these do not.

The pattern worth noticing: most defects this branch fixed originated in the *plan*,
not in the implementations. The implementers transcribed faithfully. The review gate
is what found the design errors.

## Ruling R1: T10 tells the implementer to comment out `Registry.buttons.stripFor(...)`
until T11 creates ButtonService, which a reviewer will rightly flag as dead code.
Instead, T10 defines the `ButtonService` class and `Registry.buttons` itself as a
no-arg stub that does nothing, and T11 fills in the body. Nothing is commented out at
any point, and the T10 reviewer sees a real, if empty, seam.
Cost if wrong: one extra file touched in T10; T11 rewrites the body regardless.

## Ruling R2: the plan asserts a Tink MAC tag is 44 base64 characters and sizes
chat_ref/user_ref as CHAR(44). Tink prepends a 5-byte output prefix, so an
HMAC_SHA256_256BITTAG tag is 37 bytes = 52 base64 characters, and both the column and
the CryptoTest assertion are wrong. The columns become VARCHAR(64) and the test asserts
the ref is non-empty, <= 64 chars, and stable, rather than a hard-coded width.
Cost if wrong: a wider column than strictly needed. Sizing to a guessed constant is the
larger risk, which is why the assertion becomes a bound rather than an equality.

## Ruling R3: T10's Interfaces block omits `RequestRepository.reopen`, which its own Step 3
adds. The Step 3 code is authoritative. Cost if wrong: none, documentation only.

## Ruling R4: Global Constraints ban "order"/"book"/"fill" as domain vocabulary. SQL
keywords (`ORDER BY`) and library API names are exempt. Cost if wrong: none.

## Ruling R16: the short-id lock is vacuous exactly when it matters. `SELECT ... FOR UPDATE`
locks the rows it returns, so a chat with nothing resting locks nothing — the first request
in a chat, and every request after all others close, which is a low-traffic chat's steady
state. Two concurrent creates both pick "a", and byShortId then returns an arbitrary one,
so /cancel a could act on someone else's request. Fix: a process-wide ReentrantLock around
the whole allocate-and-insert, and drop the FOR UPDATE that implied a guarantee it never
gave. This is correct because ADR 0004 fixes the architecture at one process; the comment
names that ceiling and the upgrade path (per-chat lock, then a database-level guard if the
bot is ever run as more than one instance). Rejected SERIALIZABLE isolation (heavier, and
still needs H2 to serialize a phantom it has no predicate lock for) and a unique index
(impossible to make partial in H2, and a full one would block short-id recycling).
Cost if wrong: allocation serializes globally — microseconds at chat scale.

## Ruling R17: mostRecentlyClosed ordered by row_id, which is creation order, while its name,
its description and /reopen's whole purpose ("undo my last /done") mean closure order. The
test could not detect it because it closed in creation order, so both readings agreed.
The schema had no column that could express the intent. Fix: add `closed_at`, stamp it in
transition, order by it, and rewrite the test to close in REVERSE creation order so it
discriminates. Cost if wrong: one nullable timestamp column.

## Ruling R40 (Critical, security): `done` authorised on `mine.userId == userId ||
theirs?.userId == userId`, so holding ONE valid token authorised closing BOTH requests, and
`byRefToken` is chat-agnostic and state-agnostic. Both tokens are published to every member
of the chat inside callback_data — the inline keyboard is delivered to every client — so no
guessing is needed. A modified client pairs its own token with any other it has seen and
closes a stranger's request: they are dropped from the waitlist, told nothing, and the
confirmation lands in whichever chat the presser was in. Cross-chat works too, for anyone in
both. This is the precise failure the task existed to prevent, and it came from my sketch.
Fix: the presser must own one of the two, AND the pair must be one the bot could plausibly
have suggested — same chat, opposite sides, both resting. I deliberately do NOT re-check the
size tolerance: two people may agree a swap the bot would not have introduced them for, and
`done` only records that they did. Cost if wrong: a genuine pair whose sides were somehow
equal would be refused, which the matcher could never have suggested anyway.
